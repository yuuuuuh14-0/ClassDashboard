# Manyfast 산출물 검토

검토일: 2026-10-10 · 기준: 현재 저장소의 문서와 소스 코드

## 결론

세 결과물을 모두 폐기할 필요는 없다. **기능명세서는 유지하고 구현 계약을 보완, 유저플로우는 주요 분기를 수정, HTML은 일부 화면의 시각 참고 자료로 유지하되 전체 구현 기준으로 채택하지 않는 것**을 권장한다.

아직 구현하지 않은 관리자·진도·학기 보관 기능은 기존 첫 버전 범위이므로 미구현이라는 이유로 제거하면 안 된다. 폐기할 대상은 요구사항과 충돌하는 메뉴·이동·표시, 근거 없는 추가 가정이다. 원본 3개와 앱 코드는 이번 검토에서 수정하지 않았다.

## 1. 비교 기준과 현재 상태

요구사항이 겹칠 때의 우선순위는 [README](../../README.md), [설계서](../DESIGN.md)의 안내에 따라 `DESIGN.md의 확정 요구사항 R01~R11 → PRD.md`이다. 기존 [와이어프레임](../WIREFRAMES.md)과 [개발 계획](../PLAN.md)은 작업·화면·검증 기준으로 함께 비교했다.

PRD의 교사 CRUD 설명만 읽으면 권한이 모호하지만, R03은 일반 교사의 학생·단원 편집을 금지하고 학년 관리자에게만 허용한다. 학기 보관도 R06에 이미 포함돼 있다. Manyfast 명세의 이 두 내용은 임의 확장으로 폐기할 대상이 아니다.

| 영역 | 저장소에서 확인한 현재 상태 | Manyfast 결과와의 관계 |

## 3. 유지하되 보완할 항목

### 유저플로우

- `n5`의 최초 변경 여부, `n8`의 배정 여부, `n10`의 역할, `n15`의 저장 결과, `n21`의 내 반 여부, `n47`의 전환 결과에 조건 라벨을 붙인다. 현재 연결선에는 어느 조건으로 이동하는지 표시되지 않는다.
- 로그인 실패·시도 제한·세션 만료·비활성 계정·학교 소속 중단·권한 회수 경로를 추가한다. 현재 로그인 제출과 비밀번호 제출은 성공 경로만 있다.
- 교사가 진행 학기에 미배정되어도 준비 학기에 배정된 학년 관리자라면 명단·단원 준비 경로를 제공한다. 진행·준비·보관 학기의 허용 작업을 분기한다.
- 학생 명단과 교육과정 관리 진입에 학년 관리자 이상 조건을 붙인다. 보관 자료는 현재 학교 소속, 과거 배정 범위, 이력 열람 권한 회수를 확인한 뒤 표시한다.
- 계정 비활성화는 대체 배정의 필요성을 실행 전에 검토한다. 현재 `n69 → n40`은 실행 후 담당 정리로 읽힐 수 있으므로 확인·배정 정리·비활성화의 순서를 드러낸다.
- 최초 학교의 첫 학기 시작은 기존 학기 보관 없이 진행하는 별도 경로로 표시한다. 기능명세 E25에 있는 예외를 플로우에도 반영한다.
- `푸시` 진입은 첫 버전 요구사항에 없으므로 제거한다. 일반 링크 직접 진입은 유지하되 로그인·최초 변경·대상 자원 권한 검사를 거치도록 한다.

### 기능명세서 XLSX

기능 구분과 대부분의 정책은 기존 설계와 잘 맞는다. 다음 내용을 추가하면 개발·검증 기준으로 사용하기 쉬워진다. 셀 주소는 `기능` 또는 `프로덕트 정책` 시트를 기준으로 한다.

| 위치 | 보완 내용 |
| --- | --- |
| 기능 E14/E15, 정책 D6 | 아이디 전체 유일성, 정규화, 허용 문자·길이, 비밀번호 6자 이상·72 UTF-8 바이트·현재 비밀번호와 달라야 함, 현재 비밀번호 확인을 명시. 구현된 인증 부분과 미구현 역할별 이동·관리자 웹 초기화를 따로 표시. |
| 기능 E15, 정책 D6 | 관리자 초기화 시 기존 모든 세션 차단, 최초 변경 필요 상태, 임시 비밀번호 1회 표시, 인증 서비스 변경과 DB 상태 변경 중 부분 실패의 복구 계약을 정의. 현재 SQL의 현재 세션 차단 함수만으로 관리자 초기화가 구현됐다고 보지 않는다. |

| 기능 E31, 정책 D7 | 60초 활동 신호, 탭·기기 중복 제거, 전날 로그인하고 오늘 활동한 사용자 포함, 비활성·만료 세션 제외를 추가. 현재 접속은 최근 5분 활동 기준임을 화면에도 표시. 7일 표가 선택일 기준인지 오늘 기준인지 정의. |
| 기능 E18/E31 | '학년 간 진도 편차'는 '같은 학년 학급 간 진도 차이'로 수정. '무료로 제공되는 서비스'는 PRD에 근거가 없으므로 기능 근거에서 제거하거나 별도 사업 정책으로 확인. |
| 기능 F28/F30/F31/F32 | 중간·낮은 중요도가 첫 배포 제외를 뜻하지 않도록 필수 범위와 구현 순서를 별도 열로 작성. 보관·학교 관리·통계·설명서는 기존 첫 버전 범위. |
| 기능 B2/B4/B5/G열 | 지시문 형태의 제목과 빈 프로젝트 정보를 정리. 구현 상태는 화면 샘플 생성과 구분하고 기능별 R01~R11, 기존 WF 번호, PLAN 단계, 인수 기준을 연결. |

서버 계약과 DB 상세는 XLSX에 모두 복제할 필요는 없다. 기능마다 DESIGN의 해당 절과 PLAN의 인수 기준을 연결하고, 충돌하거나 비어 있는 사용자 동작만 명세서에서 명확히 하면 된다.

### HTML 와이어프레임

- 학급 화면의 과목 요약·단원 목록, 읽기 전용 타반 화면, 명단 편집, 단원 영향 확인의 배치 아이디어는 유지한다. 인증 화면은 이미 구현된 실제 UI를 우선한다.
- 공통 상단에 학교·학기·학년/학급·역할과 접근 가능한 선택 범위를 표시한다. 단원 관리 `n29`는 적용 범위가 빠지고 영향 창 `n31`은 갑자기 5학년을 가리킨다. 영향 창의 과목도 본문에서 선택된 국어와 수학이 서로 다르다.
- 같은 가상 학교·학기·학년의 데이터로 예시를 통일한다. 현재 학급 화면은 2024학년도, 비교표는 2025학년도이며 같은 학년 국어 단원 수도 화면별로 달라 공통 교육과정인지 확인하기 어렵다. 실제 교육과정이 아닌 예시임을 표시한다.
- 학생 입력의 `학번`은 기존 명세의 `반 내 번호`로 통일한다. 선택한 학년·반을 명확히 보여주고 일반 교사·학년 관리자에게 다른 학년 선택을 허용하는 것으로 읽히지 않게 한다.
- 배정 대기의 '자동으로 대시보드 이동'은 근거 없는 동작 약속이므로 배정 다시 확인으로 교체한다. 설명서·계정·로그아웃 경로와 실제 안내 가능한 연락 방법을 포함한다.
- 빈 단원, 저장 중, 성공, 실패 복원, 버전 충돌, 권한 회수, 준비 학기, 보관 학기, 조회 실패를 별도 상태로 보여준다. 저장 실패 `n16`의 다시 시도는 현재 단순 화면 이동이므로 실패 대상과 재저장 결과를 표현한다.
- 실제 체크박스, 과목 접힘·펼침, 위·아래 순서 변경과 저장, 읽기 전용 표시를 구분한다. 현재 HTML에는 checkbox 입력과 checkbox 역할이 없고, 진도 저장 동작도 없다. 화면 배치 초안이라는 점과 기능 작동 여부를 분리한다.
- 좁은 화면의 과목 카드와 학급명 고정 비교표, 키보드 조작·입력 라벨·모달 포커스 등을 별도로 검토한다. 현 HTML의 표는 div 구성이고 값 선택·저장 동작까지 검증하는 프로토타입은 아니다.

## 4. 폐기·제외와 유지의 구분

| 판단 | 대상 |
| --- | --- |
| 폐기 또는 교체 | 학년 평균 카드, 역할 구분 없는 메뉴, 내 반도 타반으로 보내는 이동, 최초 비밀번호 변경의 취소, 계정 분실의 셀프 복구로 오해되는 안내, 근거 없는 배정 후 자동 이동·푸시 전제 |
| 일부 참고로 유지 | HTML의 과목·단원·명단·영향 확인 배치. 전체 화면이나 실제 동작의 기준으로는 보완 전 사용하지 않음 |
| 첫 버전 범위로 유지 | 학교·계정·담당·학생·단원 관리, 진도와 비교, 새 학기 준비·보관, 통계, 설명서 |
| 계속 후속 범위 | 학생 상세·개인 진도, 학생/학부모 로그인, 일괄 업로드·내보내기, 자동 학기 전환, 복수 담임 |

## 5. 기존 프로젝트 문서에도 필요한 보완

Manyfast 결과뿐 아니라 원본 기준 문서의 현황 설명도 일부 오래됐다.

- PRD에는 R03의 일반 교사/학년 관리자 구분, R04의 학년 공통 단원, R06의 학기 보관과 요구사항 우선순위를 연결한다. PRD만 외부 도구에 전달해도 같은 해석이 나오도록 정리할 필요가 있다.
- DESIGN 9장의 '실행 가능한 웹 애플리케이션이나 데이터베이스 설계는 아직 확인되지 않았다'는 현재 소스와 맞지 않는다. 기술 구성은 현재 Next.js·React·TypeScript·Supabase 의존성과 인증 구현이 있다는 상태로 갱신한다.
- PLAN의 작업 순서는 유지하되 구현 전 초안과 현재 진행 상태를 구분한다. 1단계에는 인증 구현이 있으나 관리자 웹 초기화 등 남은 작업도 있어 단계 전체 완료로 표시하면 안 된다.

이번 검토에서는 위 기존 문서의 본문도 수정하지 않았다.

## 6. 권장 반영 순서

1. PRD와 DESIGN의 확정 요구사항을 함께 제공하고 P0 권한·인증·이동·진도 표시를 먼저 수정한다.
2. XLSX 기능에 요구사항·WF·개발 단계·인수 기준을 연결하고 서버·DB 계약을 DESIGN과 연결한다.
3. 수정한 플로우 기준으로 관리자·학기·보관·통계·설명서의 누락 화면과 역할별 상태를 추가한다.
4. 실제 개발은 PLAN 순서대로 인증의 남은 작업, 학교·학기·배정 데이터와 권한, 관리자 기초 데이터, 진도 기능 순으로 진행한다. HTML에 보이는 순서로 곧바로 업무 기능을 붙이지 않는다.

## 7. 검토 범위와 한계

PRD, 기존 설계·계획·와이어프레임·인증 문서, 현재 앱/인증 SQL/테스트 코드, Manyfast Markdown, XLSX의 두 시트 전체, HTML의 화면·텍스트·이동 스크립트를 비교했다. 누락 ID와 입력 유형은 소스 파싱으로 확인했다.

Edge를 통한 렌더링 확인은 환경의 프로세스 실행 제한(`spawn EPERM`)으로 수행하지 못했다. 따라서 실제 화면의 줄바꿈·반응형 배치·시각 품질과 브라우저 클릭 결과는 검증 완료로 간주하지 않는다. 로그인 버튼의 고정 이동과 없는 대상의 무반응은 HTML의 이벤트 처리 소스를 근거로 판단했다. 실제 Supabase와 계정·비밀번호·배정 데이터는 변경하지 않았다.
