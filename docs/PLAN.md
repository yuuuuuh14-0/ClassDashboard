# 학급 진도 대시보드 개발 계획서

작성일: 2026-10-07 · 문서 상태: 구현 전 계획 초안

첫 배포 목표는 선생님이 담당 반의 진도를 기록하고 같은 학년의 진도를 비교하며, 관리자가 학교 운영과 학기별 보관을 수행할 수 있는 프로그램이다. 권한과 학기 데이터 구조를 먼저 확정하고, 실제 사용 흐름을 단계별로 완성한다.

요구사항과 데이터·화면·기술 설계는 [설계서](DESIGN.md)를 따른다. 이 계획은 앞으로 수행할 작업과 완료 기준이며, 구현이나 검증이 이미 끝났다는 의미가 아니다.

## 1. 개발 원칙과 범위

- 첫 버전에 PRD의 관리자 기능, 이용 통계, 설명서, 학기 보관을 포함한다.
- 일반 선생님은 담당 반 진도를 수정할 수 있지만 학생·과목·단원을 수정할 수 없다.
- 학년 관리자의 공통 단원 변경은 해당 학교·학기·학년 전체에 적용한다.
- 데이터베이스의 학교·학년 경계와 보관 학기 보호를 화면 구현보다 먼저 검증한다.
- 학생 명단 기능은 포함하고 학생 상세 화면과 개인별 학습 기록은 후속 범위로 둔다.
- 실제 학교 데이터를 넣기 전까지 가상 학교·교사·학생으로 검증한다.
- 문서 작성 단계에서는 외부 서비스 생성, 실제 배포, 실데이터 등록을 수행하지 않는다.

## 2. 단계별 진행 순서

```mermaid
flowchart LR
    A[0 설계 정리와 화면 초안] --> B[1 개발 기반과 인증 검증]
    B --> C[2 DB와 접근 권한]
    C --> D[3 학교 구성과 관리 기능]
    D --> E[4 진도와 대시보드]
    E --> F[5 학기 전환과 보관]
    F --> G[6 통계와 설명서]
    G --> H[7 통합 검증과 시범 운영]
```

각 단계의 완료 기준을 통과한 뒤 다음 단계로 진행한다. 데이터 구조·권한·학기 전환 검증은 후반으로 미루지 않는다.

| 단계 | 주요 산출물 | 선행 조건 | 작업일 추정 |
| --- | --- | --- | --- |
| 0 | 권한표, 화면 초안, 데이터 관계, 구현 기본안 정리 | 현재 설계 문서 | 1~2일 |
| 1 | 실행 가능한 프로젝트, 인증 연결 검증, 개발 환경 | 0 | 2~3일 |
| 2 | DB 마이그레이션, 접근 정책, 권한 검증 데이터 | 1 | 3~5일 |
| 3 | 학교·계정·배정·학생·단원 관리 화면 | 2 | 4~6일 |
| 4 | 진도 체크, 학급·학년 대시보드 | 3 | 3~5일 |
| 5 | 다음 학기 준비, 원자적 전환, 보관 조회 | 4 | 3~5일 |
| 6 | 이용 통계, 설명서, 상태 표현과 화면 개선 | 5 | 2~3일 |
| 7 | 통합 테스트, 복원 검증, 시범 운영 결과 | 6 | 4~6일 |
| 합계 | 첫 버전 개발과 검증 | 전담 개발자 1명 기준 가정 | 22~35작업일 |

위 일정은 기능 범위가 유지되고 검토·환경 준비가 원활하다는 가정에 따른 초기 추정이다. 운영 계정 준비, 학교 검토 대기, 실제 데이터 정리와 후속 요구사항은 별도다. 날짜별 확정 일정은 1단계의 인증 연결 및 환경 검증 후 산정한다.

## 3. 단계별 작업과 완료 기준

### 0단계 설계와 화면 초안

주요 화면의 배치와 이동 흐름은 [와이어프레임](WIREFRAMES.md)을 기준으로 검토한다.

작업:

- 확정 요구사항 R01~R11과 설계 기본안을 구분한다.
- 로그인, 학급 대시보드, 학년 대시보드, 학생·단원 관리, 담당 배정, 학기 전환, 이용 통계의 화면 초안을 만든다.
- 정상 상태뿐 아니라 단원 없음, 미배정 계정, 저장 실패, 읽기 전용 보관 화면을 설계한다.
- 교사 1인 1학급, 과거 자료 열람 범위, 관리자 발급 계정 방식을 초기 구현 기본안으로 기록한다.
- 정확한 기술 버전, DB 운영 방식과 개발 환경을 선택한다.

완료 기준: 학생·단원 편집 권한과 진도 체크 권한을 혼동하지 않는 화면·권한표가 있고, 사용자 역할마다 시작 화면과 작업 경로가 정리되어 있다.

### 1단계 개발 기반과 인증 연결

작업:

- Next.js와 TypeScript 프로젝트를 구성하고 실행·빌드·검증 명령을 정리한다.
- Supabase 개발 환경을 구성하고 개발·검증·운영 설정을 분리한다.
- 환경 변수 예시 파일을 만들고 인증 비밀 값이 저장소에 포함되지 않게 한다.
- 서버의 아이디 연결을 통한 비밀번호 로그인을 실제 인증 서비스에서 작게 검증한다.
- 관리자 발급, 최초 비밀번호 변경, 관리자 초기화, 로그아웃, 세션 만료를 검증한다.
- 공개 회원가입을 차단하고 내부 인증 식별자에 메일이 발송되지 않는 설정을 확인한다.
- 최초 사이트 관리자 생성 절차와 인증 계정·프로필 생성 실패 시 복구 절차를 만든다.

완료 기준: 아이디와 비밀번호만으로 로그인하고, 로그아웃·만료·초기화된 세션으로 업무 요청을 계속할 수 없다. 초기 비밀번호 변경 전에는 업무 화면과 직접 데이터 접근이 차단된다. 연결 방식에 제약이 발견되면 이 단계에서 해결하고 이후 기능으로 넘기지 않는다.

### 2단계 데이터베이스와 권한

작업:

- 설계서 7장의 테이블, 외래 키, 유일 조건, 인덱스를 마이그레이션으로 작성한다.
- 학교 소속, 학기별 담당 배정, 학년 관리자 지정과 과거 열람 권한 회수를 구현한다.
- 테이블 접근 권한과 RLS, 조회용 뷰·함수의 접근 범위를 설정한다.
- 학교·학기·학년이 다른 학급과 단원을 연결할 수 없도록 제약을 둔다.
- 학기 상태에 따른 데이터 변경 제한과 학기 전환 잠금 규약을 구현한다.
- 변경 충돌, 감사 기록, 비활성화 정책을 공통 처리한다.
- 두 학교, 여러 학년, 서로 다른 역할의 가상 계정을 준비한다.

완료 기준: 서버와 DB 접근 테스트에서 허용할 작업은 성공하고 금지할 작업은 실패한다. 식별자 조작과 직접 DB API 요청으로 다른 학교·학년·학생 정보에 접근할 수 없다.

### 3단계 관리자 기능과 기초 데이터

작업:

- 사이트 관리자의 학교 생성·관리와 학교 관리자 배정을 구현한다.
- 학교 관리자의 학기·학년·학급 구성, 선생님 계정 관리와 담당 배정을 구현한다.
- 학년 관리자 지정·교체를 구현한다. 다른 학년 교사를 지정하거나 자기 권한을 높이는 요청을 막는다.
- 학년 관리자의 학생 명단 CRUD와 같은 학년 내 반 이동을 구현한다.
- 학년 공통 과목·단원 CRUD, 순서 변경, 비활성화·복구를 구현한다.
- 일반 선생님에게 관리 메뉴를 숨기고 직접 변경 요청도 거부한다.
- 등록·변경·삭제의 적용 범위와 저장 상태를 화면에 표시한다.

완료 기준: 관리자가 새 학교를 개설하고 학기·학급·교사·학생·단원을 준비할 수 있다. 학년 관리자가 수정한 단원은 같은 학년 모든 반에서 같은 목록으로 조회되며, 다른 학년에는 영향을 주지 않는다.

### 4단계 진도 기록과 대시보드

작업:

- 담당 반 단원 체크·해제와 버전 기반 충돌 처리를 구현한다.
- 과목별 완료 수·전체 수·진도율을 서버에서 같은 규칙으로 계산한다.
- 학급 대시보드와 담당 반 학생 명단 조회를 구현한다.
- 학년 비교표와 다른 반의 읽기 전용 단원 진도 보기를 구현한다.
- 학생 정보가 진도 비교 응답에 포함되지 않게 한다.
- 단원 추가·비활성화 시 진도율 변화 안내를 구현한다.
- 저장 실패 복구, 중복 클릭 방지, 재조회·포커스 복귀 시 데이터 갱신을 구현한다.
- PC·태블릿·좁은 화면의 표시와 키보드 조작을 확인한다.

완료 기준: 일반 선생님이 자기 반 진도를 저장하고 새로고침해도 같은 값을 확인한다. 다른 반은 진도만 조회할 수 있고 진도 수정과 학생 조회는 차단된다.

### 5단계 학기 전환과 보관

작업:

- 학교별 준비·진행·보관 학기 상태와 학기 선택기를 구현한다.
- 이전 학기에서 복사할 학급·명단·과목·단원을 선택하고 새로운 ID로 준비한다.
- 복사한 정보의 중복 생성과 편집 내용의 자동 덮어쓰기를 막는다.
- 교사·학년 관리자 배정을 검토하고 전환 결과를 미리 보여준다.
- 보관 정보 저장, 기존 학기 잠금, 새 학기 활성화, 감사 기록을 하나의 트랜잭션으로 처리한다.
- 요청 재시도·동시 전환·진도 저장과 전환의 경합을 처리한다.
- 과거 학기의 당시 이름·단원·명단·진도를 읽기 전용으로 보여준다.
- 학교 소속 해제와 과거 자료 열람 권한 회수를 보관 조회에도 적용한다.

완료 기준: 새 학기 진도는 미완료에서 시작하고, 이전 학기 자료는 그대로 유지된다. 처리 중 실패하면 이전 학기가 계속 활성 상태이며, 같은 요청을 다시 보내도 중복 전환되지 않는다. 사이트 관리자도 일반 기능으로 보관 원본을 수정할 수 없다.

### 6단계 이용 통계와 설명서

작업:

- 성공한 로그인, 날짜별 실제 이용자, 최근 활동을 집계한다.
- 학교별 계정·접속 현황과 전체 사이트 대시보드를 만든다.
- 여러 탭·기기에서 같은 사용자를 중복 집계하지 않도록 한다.
- 한국 시간 자정 경계와 전날부터 이어지는 세션의 당일 이용을 처리한다.
- 일반 선생님, 학년 관리자, 학교 관리자, 사이트 관리자별 사용 설명서를 작성한다.
- 보관 자료 조회, 단원 추가 시 퍼센트 감소, 잘못된 체크 해제 방법을 설명한다.

완료 기준: 통계 값이 가상 이벤트와 일치하고 집계 기준이 화면에 표시된다. 각 역할이 설명서를 따라 첫 작업과 학기 전환을 수행할 수 있다.

### 7단계 통합 검증과 시범 운영

작업:

- 아래 인수 시나리오를 실제 브라우저와 API·DB 테스트로 검증한다.
- 두 학교의 동시 사용, 권한 변경 후 열린 화면, 저장 실패와 재시도를 점검한다.
- 가정한 데이터 규모와 동시 로그인 사용자 50명 환경에서 응답 시간을 측정한다.
- 운영 호스팅·DB 설정, 로그, 오류 확인 경로, 비밀 값 관리를 점검한다.
- 백업으로 별도 검증 DB를 복원해 학교·학기·진도·보관 기록의 일치를 확인한다.
- 가상 데이터 시범 운영 후 지정된 학교에서 실제 사용 흐름을 확인한다.
- 배포 절차, DB 마이그레이션 순서, 실패 시 복구 방법, 운영 설명서를 정리한다.

완료 기준: 필수 인수 시나리오가 모두 통과하고, 접근 범위 오류·데이터 손실·학기 전환 오류가 남아 있지 않다. 실데이터 도입에 필요한 보관 기간·탈퇴 처리·운영 권한도 정해져 있다.

## 4. 요구사항별 인수 시나리오

| 검증 항목 | 요구사항 | 합격 기준 |
| --- | --- | --- |
| 아이디 로그인 | R01 | 이메일 입력 없이 로그인 가능, 틀린 비밀번호 거부, 로그아웃 후 보호 화면 접근 차단 |
| 계정 발급·초기화 | R01, R08, R09 | 자기 관리 범위의 계정만 발급·초기화, 초기 비밀번호 변경 전 업무 차단 |
| 선생님 화면 | R02 | 담당 반·학년 대시보드 사용 가능, 학생 상세 기능은 아직 제공하지 않음 |
| 학생·단원 수정 제한 | R03 | 일반 교사의 버튼·직접 요청·DB API 변경 모두 거부, 학년 관리자는 자기 학년에서 성공 |
| 학년 관리자 진도 권한 | R03, R07 | 자기 반 진도는 수정 가능, 다른 반 진도 수정은 불가 |
| 공통 단원 수정 | R04 | 같은 학년 모든 반에 반영, 다른 학교·학년·학기에는 변화 없음 |
| 기본 진도율 | R05 | 10개 중 4개 완료 시 40.0%, 체크 해제 후 30.0% |
| 빈 단원과 반올림 | R05 | 0개 단원은 미등록 표시, 3개 중 1개 완료 시 33.3% |
| 단원 추가 | R04, R05 | 4/10에서 단원 하나 추가 시 모든 해당 반의 분모 증가, 예시 반은 4/11과 36.4% |
| 단원 비활성화·복구 | R04, R05 | 완료 기록 보존, 유효 단원으로 계산, 복구하면 이전 완료 상태가 되살아남 |
| 학생 명단 변경 | R03 | 같은 학년 내 반 이동 가능, 다른 학년 이동은 학교 관리자, 진도에는 영향 없음 |
| 학교·학년 격리 | R07 | URL과 요청의 학교·학년·학급 ID를 조작해도 타 범위 정보 노출 없음 |
| 타 반 정보 제한 | R07 | 같은 학년 타 반 진도는 보이지만 학생 이름·명단·상세 정보는 노출되지 않음 |
| 권한 회수 | R07, R08 | 배정 해제·계정 비활성화 후 기존 세션의 다음 업무 요청 차단 |
| 학교 관리자 범위 | R08 | 자기 학교 구성·권한 부여 성공, 학교 생성과 타 학교 조회·변경 실패 |
| 사이트 관리자 범위 | R09 | 학교 생성과 학교 관리자 배정, 학교별 관리 화면 접근 성공 |
| 학기 보관 정확성 | R06 | 보관 후 예전 학급·명단·단원·완료 수·진도율이 전환 직전과 일치 |
| 다음 학기 독립성 | R06 | 새 학기 데이터는 새 ID, 진도 미완료, 현재 자료를 수정해도 과거 값 유지 |
| 보관 변경 차단 | R06 | 모든 앱 역할의 일반 변경과 직접 DB API 변경 거부, 보관 학기로의 행 이동도 거부 |
| 전환 실패·재시도 | R06 | 중간 실패 시 이전 학기 유지, 재시도 성공, 완료 요청 재전송은 같은 결과 반환 |
| 전환 경합 | R06 | 동시 전환과 진도 저장에도 활성 학기 한 개 유지, 보관 직후 늦은 저장은 거부 |

## 5. 검증용 데이터

기능 검증은 최소 다음 데이터로 진행한다.

| 구분 | 구성 |
| --- | --- |
| 학교 | 가상 A학교, B학교 |
| 학기 | 2026학년도 1학기와 2학기, 2027학년도 1학기 준비 자료 |
| 학년·학급 | 각 학교 3학년·4학년, 학년마다 1반·2반 |
| 계정 | 사이트 관리자, 학교별 관리자, 각 반 담임, 학년별 관리자, 미배정·비활성 계정 |
| 학생 | 동명이인, 서로 다른 반의 같은 번호, 전출·반 이동 사례 |
| 과목·단원 | 단원 0개·3개·10개 과목, 완료·미완료·비활성 단원 |
| 이력 | 교사 교체, 학년 관리자 교체, 학교 소속 해제, 과거 조회 권한 회수 |

이 데이터로 정확성을 검증한 뒤, 별도 생성한 대량 데이터로 성능을 측정한다. 성능 목표와 관측값을 구분해서 기록한다.

## 7. 첫 배포 완료 기준

- [ ] R01~R11에 연결된 필수 시나리오가 모두 통과한다.
- [ ] 학교·학년·학급 경계를 넘는 조회·변경이 차단된다.
- [ ] 일반 교사와 학년 관리자의 편집 권한이 요구사항대로 다르다.
- [ ] 단원 변경과 진도 계산이 모든 관련 화면에서 일치한다.
- [ ] 학기 전환 실패·동시 실행·재시도와 과거 기록 보존이 검증됐다.
- [ ] 로그인·초기화·세션·권한 회수 동작이 검증됐다.
- [ ] PC·태블릿에서 주요 작업이 가능하고 저장 실패와 읽기 전용 상태가 명확하다.
- [ ] 통계의 계산 기준과 실제 값이 일치한다.
- [ ] 역할별 사용 설명서와 운영·복구 설명서가 준비됐다.
- [ ] 성능 측정 환경, 목표 대비 결과와 남은 제약이 기록됐다.
- [ ] 호스팅·DB 운영 설정, 백업 복원, 데이터 보관·삭제 방침이 정해졌다.
- [ ] 가상 데이터와 실제 운영 데이터가 분리되어 있다.

## 8. 구현 착수 시 첫 작업

첫 구현 작업은 **아이디 로그인 검증과 학교·학기·역할 데이터 기반 구성**이다. 이를 통해 인증 방식과 접근 범위가 실제 환경에서 성립하는지 먼저 확인한다. 이후 `학교 개설 → 교사 배정 → 학생·단원 준비 → 진도 기록 → 다음 학기 전환` 순서로 한 흐름씩 완성한다.

학생 상세 화면, 개인별 학습 기록, 대량 업로드, 데이터 내보내기, 자동 학기 전환, 복수 담임은 첫 버전 이후 별도 요구사항과 일정으로 다룬다.
